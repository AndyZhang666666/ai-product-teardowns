# 字节豆包 拆解

**拆解日期**：2026-09
**体验方式**：iOS App + 网页端免费账号，约两个月，另做约 20 组对照测试
**一句话结论**：它的最大产品难题不是能力，是「用户不知道该期待什么」。

---

## 1. 目标用户与场景

**服务的时刻**：没形成 AI 习惯的普通人，遇到具体小麻烦时随手问一句。它优化的是从念头到答案的路径长度，不是答案的天花板——交互重心全在压缩启动成本：按住即说、拍照问、划词唤起。

**谁不在用户群里**：需要稳定复现结果的工作流用户。对话不可版本管理，要「同一提示词跑一百次」的人没有工具支撑。

## 2. 能力边界

**做得对的**：图片理解最稳（拍题、表格截图、手写笔记，测试中没失手）；长文档提取要点稳定。

**开始退化的条件**：

- **多步计算会中途出错，且叙述依然流畅。** 算复合增长率，公式对、步骤对、最后一步数值错，结论却很确定——**过程正确性掩盖了结果错误性**。
- **联网检索质量取决于「可搜索性」。** 有明确出处的答得准；需要综合判断的会把几篇观点文章当事实综合。
- **多轮对话指令衰减。** 第一轮设定「都用表格」，五六轮后悄悄退回散文。

**一个可验证的例子**：问「2026 上半年国内 AI 领域值得关注的融资」，给出带公司名、金额、投资方的整齐清单。抽查三条，两条对得上公开报道，一条金额不一致。**清单形式本身传递了「已核实」的暗示，实际并没有。**

## 3. 实现路径推测

> 以下为推测。

**推测**：多模型路由 + 分层推理深度 + 检索增强。

**依据**：不同类型问题的首 token 延迟呈**离散档位**而非连续分布——离散是路由的典型特征。时效类问题空白期结束后文字连贯吐出不停顿——检索在生成前完成。

**对产品判断的影响**：如果路由存在，**体验方差主要来自路由准确性，而非模型能力**。本该走深度推理的问题被路由到快速通道，用户看到的就是「豆包变笨了」，且无法感知发生了什么。这解释了为什么同一类问题在不同时候的质量差异，比不同类问题之间的差异更大。

## 4. 失败与兜底

**错的时候长什么样**：语气、格式、置信度全不变，错的那条和对的两条在呈现上无法区分。

**兜底缺失的**：「AI 生成可能有误请核实」是**全局免责**，对每句话说同样的话等于都没说。更关键的是**没把「有检索来源」和「纯靠模型记忆」区分开**——风险差一个数量级，界面上长得一样。

## 5. 效果怎么衡量

通用助手最难定指标，因为**没有单一任务**。先按意图分层，再在层内定指标。

| 类别 | 指标 |
|---|---|
| 使用类 | 日活、**多模态入口使用占比**（差异化所在） |
| 质量类 | **追问率**（同会话内为同一意图再次发问） |
| 质量类 | **会话内放弃率**（提问后不再交互直接关闭） |
| 价值类 | 回访率按意图拆分 |

**为什么追问率是核心**：唯一不需要标注就能大规模反映「答案不够好」的信号。但有陷阱——**追问也可能是答得好、用户想深入**，所以必须和放弃率一起看：追问高+放弃低 = 在深挖；追问高+放弃高 = 在挣扎。单看一个都会误判。

**最缺的是路由准确性的可观测性**——要衡量得先有「这问题本该走哪条路」的人工标注。典型的「最重要的指标最难埋」。

## 6. 商业化路径

**付费门槛**：卡在高消耗动作次数和高峰期优先级上，日常问答基本不设限——先占入口，不是先赚钱。

**是否对齐**：时机准，但有结构性问题——**免费版足够好，是获客优势也是转化障碍。** 普通用户永远碰不到付费墙，付费用户被压缩到少数重度用户，而这批人最会算成本、最容易流向 API。所以产品持续往办公任务、PPT、表格长——**不是能力扩张，是在制造付费场景。**

## 我不同意的地方

**不同意把不确定性处理成一句全局免责声明。** 用户三天就脱敏，之后它只承担法律责任，不承担产品责任。产品内部明明知道这次有没有走检索——**信息是已知的，只是没告诉用户**，大概担心显示「本次未检索」会让用户觉得产品不行。这个担心是错的。**用户对 AI 的信任不建立在「它总是对」，而建立在「我知道什么时候该信它」。** 永远自信的助手被坑一次就全面降级信任；会说「这次不太确定」的助手，用户会学会分场景用。

## 我会做的下一步

1. **给回答加「依据来源」分类标签**，三档：带检索来源（可点开）、基于模型知识（提示时效风险）、需要计算（建议验算）。信息内部已有，成本主要在 UI。验证：带标记的回答采纳率是否显著高于无标记。

2. **多步计算类任务强制加一步独立验算。** 同一模型再算一遍比对，成本翻倍但能抓住大部分算术错误。我做评估工具时验证过同一模型多次判断存在方差（见 [llm-output-eval](https://github.com/AndyZhang666666/llm-output-eval) 的一致性检查），这个方差恰好可用来交叉验证。

## 局限

免费账号的外部观察。实现路径为推测，效果指标是我假设的 PM 视角，不写价格数字。
