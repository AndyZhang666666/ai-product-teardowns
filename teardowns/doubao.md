# 字节豆包 拆解

**拆解日期**：2026-09
**体验方式**：iOS App + 网页端，免费账号，日常使用约两个月，其中针对本次拆解做了约 20 组对照测试
**一句话结论**：它是唯一一个把「多模态」做成了默认交互而不是功能入口的国产助手——但它最大的产品难题不是能力，是「用户不知道该期待什么」。

---

## 1. 目标用户与场景

**它服务的具体时刻**：一个没有形成「AI 使用习惯」的普通人，在遇到一个具体的小麻烦时（一道题不会讲、一份 PDF 太长、一句外语看不懂、一个东西不认识），打开手机随手问一句。关键在「随手」——它优化的是从产生念头到得到答案的路径长度，不是答案的天花板。

证据是它的交互重心：语音按住即说、拍照直接问、划词唤起。这些都是在压缩「启动成本」，而不是在提升「单次质量上限」。

**谁明确不在它的用户群里**：需要稳定复现结果的专业工作流用户。它的产品形态是对话，对话是一次性的、不可版本管理的。一个需要「同一个提示词跑一百次、对比效果、固化成模板」的人，在这里没有任何工具支撑。

另一类是对信息来源有强审计要求的人。它给的答案里，可核实的来源标注是弱项——不是完全没有，而是不构成一个可依赖的机制。

## 2. 能力边界

**做得对的**：

- **图片理解是它最稳的能力。** 拍一道题、一张表格截图、一份手写笔记，识别和结构化提取都很稳。这一条在我测的所有场景里没失手。
- **长文档提取要点**稳定可用，几十页的 PDF 能给出可信的结构和摘要。
- **口语化改写**质量高，把书面语转成能说出口的话，这类任务它做得比很多同类好。

**开始退化的条件**：

- **需要多步精确计算时会中途出错，且出错时叙述依然流畅。** 我给它一组销售数据算复合增长率，它列出了正确的公式、正确的中间步骤，最后一步算错了数值，但结论写得很确定。这是最危险的一类失败——**过程正确性掩盖了结果错误性**，用户看到步骤都对就不验算了。
- **联网检索的结果质量取决于问题的「可搜索性」**。问「某公司最新财报营收」这类有明确出处的，答得准；问「某个行业今年的趋势」这类需要综合判断的，它会搜到几篇观点文章然后当成事实综合，看起来有依据实际上是二手观点的平均。
- **多轮对话中的指令衰减。** 在第一轮设定「所有回答都用表格」，到第五六轮之后会悄悄退回散文。它不会说「我忘了」，就是不做了。

**一个具体的可验证例子**：我问「2026 年上半年国内 AI 领域有哪些值得关注的融资」，它给出了一份带公司名、金额、投资方的清单，格式整齐、语气确定。抽查其中三条，两条能在公开报道里对上，一条的金额与我能找到的报道不一致。**清单形式本身传递了一种「已核实」的暗示，而实际上并没有。** 这不是它独有的问题，但它的排版做得越整齐，这个暗示越强。

## 3. 实现路径推测

> 以下为推测，依据为外部可观察线索，不代表官方架构。

**推测**：多模型路由 + 按模式分层的推理深度 + 检索增强，三者组合。不是单一模型在支撑所有场景。

**依据**：

- **路由存在的证据**：不同类型问题的首 token 延迟差异极大。简单闲聊几乎瞬时；一旦问题涉及时效信息或复杂推理，会先有一段明显的空白期。这个空白期长度不是随问题长度线性变化的，而是呈现出几个离散的档位——**离散档位是路由的典型特征**，如果是同一模型处理，延迟应该是连续分布。
- **推理深度分层的证据**：产品自己把这件事显式化了（不同的模式选项），这反而是最强的证据——它承认了不同深度对应不同成本。
- **检索发生在生成前而非生成中的证据**：涉及时效信息的回答，那段空白期结束后文字是连贯吐出的，中间不再停顿。如果是边生成边检索，应该能观察到中途卡顿。
- **安全层前置且独立**：敏感话题的拒绝响应速度远快于正常回答，措辞高度模板化。

**这个推测对产品判断的影响**：如果路由确实存在，那么**用户体验的方差主要来自路由判断的准确性，而不是模型能力**。一个本该走深度推理的问题被路由到了快速通道，用户看到的就是「豆包变笨了」。这解释了一个我实际感受到的现象：同一类问题在不同时候的回答质量差异，比不同类问题之间的差异更大。而用户完全无法感知路由发生了什么——这是下面第五节要说的核心问题。

## 4. 失败与兜底

**它错的时候长什么样**：语气不变、格式不变、置信度不变。上面那个融资清单的例子就是典型——错误的那一条和正确的那两条在呈现上完全无法区分。

**它自己知不知道错了**：在「不知道」和「知道但不说」之间。有些明显超出能力范围的问题它会拒答或声明局限，说明存在某种边界判断；但对于「答得出但答错了」的情况，没有任何机制标记。

**兜底做得好的地方**：

- 页面上有「AI 生成可能有误请核实」的常驻提示。诚实，但也仅止于诚实——**这是一句全局免责，不是针对具体内容的不确定性提示**。它对每一句话说同样的话，等于对每一句话都没说。
- 深度模式下会给出检索来源，用户可以点开核对。这是真兜底。

**兜底缺失的地方**：**没有把「这次回答的可靠性」和「上次回答的可靠性」区分开。** 用了检索、有来源的回答，和纯靠模型记忆生成的回答，在界面上长得一样。用户没有任何线索判断该不该核实。这是我认为它最重要的一个产品缺口。

## 5. 效果怎么衡量

通用助手的评测维度最难定，因为**它没有单一任务**。同一个入口既处理闲聊也处理专业分析，任何单一质量指标都会被稀释。我的做法是先按意图分层，再在层内定指标。

| 类别 | 指标 | 为什么 |
|---|---|---|
| 使用类 | 日活、人均日会话数、**多模态入口使用占比** | 第三个是它的差异化，要单独看 |
| 质量类 | **追问率**（同一会话内用户为同一意图再次发问的比例） | 见下 |
| 质量类 | **会话内放弃率**（提问后不再交互也不采纳，直接关闭） | 失败的沉默信号 |
| 质量类 | 复制/分享/导出率 | 「答案被拿去用了」的正向信号 |
| 价值类 | 次日/7日回访率，按意图类型拆分 | 哪类需求真正留住了人 |
| 价值类 | 付费转化率与转化前的行为路径 | 什么动作让人愿意付钱 |

**为什么追问率是核心质量指标**：它是唯一一个不需要标注、不需要人工评审，就能大规模反映「答案不够好」的信号。用户重新问一遍，几乎一定是因为第一次没满足。而且它能按意图分层统计——如果「计算类」问题的追问率显著高于「翻译类」，那就直接定位到了能力短板。

但它有个陷阱：**追问也可能是因为答得好、用户想深入**。所以必须和「放弃率」一起看：追问率高 + 放弃率低 = 用户在深挖，是好事；追问率高 + 放弃率高 = 用户在挣扎，是坏事。单看任何一个都会误判。

**现在最缺的是路由准确性的可观测性。** 上面第三节推测存在路由，那么就存在「路由错了」这种失败模式。但从外部完全看不到，我推测内部也未必有对应指标——因为要衡量它，你得先有「这个问题本该走哪条路」的标注，而这需要人工。这是一个典型的「最重要的指标最难埋」的例子。

## 6. 商业化路径

**付费门槛卡在哪个动作前面**：卡在高消耗动作的次数上（图片视频生成、深度模式、长文档），以及高峰期的优先级。日常问答基本不设限。

**免费额度的设计意图**：拉新且培养习惯。免费能力的宽度远超同类——这个策略指向的是「先占住入口」，而不是「先赚钱」。字节有这个打法的资源。

**付费点和价值时刻是否对齐**：**对齐得比可灵好，但有一处结构性问题。**

对齐的部分：付费解锁的是「更多次数」和「更快」，这两件事用户在被限制的当下能立刻感知到需求。你正在做一件事，被告知额度用完了——此刻付费意愿最高。这个时机是准的。

结构性问题在于：**免费版足够好，是获客优势，也是转化障碍。** 一个普通用户的日常需求几乎全在免费范围内，他永远碰不到付费墙。于是付费用户被压缩到少数重度用户——而这批人恰恰是最会算成本、最容易流向 API 或竞品的一群。

所以它的商业化真正要解决的不是「怎么让人付钱」，而是「怎么让普通用户产生高价值需求」。这解释了产品为什么持续往办公任务、PPT、表格这些方向长——**这些不是能力扩张，是在制造付费场景。** 一个人做 PPT 的需求，比闲聊的需求更容易被定价。

## 我不同意的地方

**我不同意把不确定性处理成一句全局免责声明。**

「AI 生成可能有误请核实」这句话贴在每一次回答下面，实际效果等于没贴。用户三天就对它脱敏，之后它只承担法律责任，不承担产品责任。

而这个产品明明有能力做得更好：它内部知道这次回答有没有走检索、有没有拿到来源、有没有走深度推理。**这些信息是已知的，只是没有告诉用户。**

一个纯靠模型记忆生成的、关于最新数据的回答，和一个带三条来源的回答，风险等级差一个数量级，但界面上完全一样。这不是技术限制，是产品选择——大概是担心显示「本次未检索」会让用户觉得产品不行。

我认为这个担心是错的。**用户对 AI 的信任不是建立在「它总是对」上，是建立在「我知道什么时候该信它」上。** 一个永远自信的助手，用户被坑一次就会全面降级信任；一个会说「这次我不太确定」的助手，用户会学会分场景使用它——后者的长期使用深度更高。

## 我会做的下一步

1. **给回答加一个轻量的「依据来源」标记，不是免责声明，是分类标签。** 三档就够：带检索来源（可点开）、基于模型知识（提示时效风险）、需要计算（提示建议验算）。这些信息系统内部已有，成本主要在 UI 和一次分类判断。验证方式：看用户对带来源标记的回答的采纳率是否显著高于无标记的——如果是，说明这个标记正在帮用户做决策，而不是在制造焦虑。

2. **在多步计算类任务上，强制加一步独立验算。** 上面那个复合增长率算错的例子，用同一个模型再算一遍并比对结果，成本是翻一倍的 token，但能抓住大部分算术错误。可以只对识别为计算类的任务启用。这件事我在做评估工具的时候验证过一个相关结论：同一个模型对同一段内容的多次判断存在方差（见 [llm-output-eval](https://github.com/AndyZhang666666/llm-output-eval) 的一致性检查），而这个方差恰恰可以用来做交叉验证——两次算出同一个数，比一次算出来可信得多。

## 局限说明

以上全部基于免费账号的外部观察，未覆盖付费版能力和企业版。实现路径为推测，依据是延迟、模板化程度这类外部线索，不代表字节团队的真实架构。效果指标是我假设的 PM 视角。功能与定价随版本变动频繁，本文不写具体价格数字。
