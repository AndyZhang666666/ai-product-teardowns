# AI Product Teardowns

用同一套六维框架拆解国内 AI 产品。目前三篇：快手可灵、字节豆包、百度文库 AI。

## 这个仓库为什么存在

拆解 AI 产品不是写测评。测评回答「它好不好用」，拆解回答四个问题：

1. 它的能力边界在哪——什么情况下一定做不对？
2. 它答错的时候怎么办——用户能不能发现？
3. 它的效果怎么衡量——如果我是 PM，看哪几个指标？
4. 如果我是 PM，下一步做什么——具体到功能。

这四个问题，用过产品的人和能负责产品的人，答案会不一样。这个仓库是练第二种答法。

## 框架

六个维度固定不变，每篇按同一顺序走。**同一把尺子量三个产品，结论才可比**——否则拆完就是三篇孤立的读后感。

| 维度 | 核心问题 |
|---|---|
| 目标用户与场景 | 服务谁的什么时刻？**谁明确不在用户群里？** |
| 能力边界 | 做对什么、什么条件下一定做不对？要有可验证的例子 |
| 实现路径推测 | 提示词 / 检索 / 微调 / 路由？依据是什么外部线索？ |
| 失败与兜底 | 答错时长什么样？它自己知道吗？用户能低成本核实吗？ |
| 效果怎么衡量 | 看哪几个指标？现在最缺哪个？必须给指标名 |
| 商业化路径 | 付费点卡在哪个动作前？和价值时刻对齐吗？ |

外加两节必填：**「我不同意的地方」**（只夸不批等于没判断）和 **「我会做的下一步」**（具体到功能、可验证）。

每个维度为什么重要、怎么写才算写到位，见 [FRAMEWORK.md](FRAMEWORK.md)。可复制的模板见 [TEMPLATE.md](TEMPLATE.md)。

三篇的写作约束：中文、800-1500 字、每篇至少 1-2 个可验证的具体例子、必须有反对意见和具体下一步。

## 三篇放在一起看到的事

单独看每篇是三个产品的判断，放在一起看是同一个问题的三种答法——**AI 产品的付费点该设在哪**：

- 可灵设在「每次生成」，用户为失败付钱，新手成本最高、也最价格敏感。
- 豆包基本不设，免费太好用反而碰不到墙，只能靠制造新的付费场景（办公、PPT）。
- 文库设在「下载」，和价值时刻高度对齐，但代价是产品形态被锁死在「可下载的成品」上。

三个都不是错的选择，但每个都有一个不可回避的代价。这个对照是我做完三篇之后才看清的。

## What I'd improve next

诚实的局限：

- **底层实现全部是黑盒推测。** 我没有任何一家的内部数据，实现路径那一节的依据是延迟、模板化程度、多次生成的方差这类外部线索。它们指向某个方向，但不构成证据。
- **效果衡量部分是我的假设，不是官方指标。** 我写的是「如果我是 PM 会看什么」，这些团队实际看什么我不知道。
- **样本量小。** 每个产品几十次使用的量级，能发现模式，不足以做统计结论。所有「一定做不对」的说法都该读成「在我的测试中稳定复现」。
- **单人视角，没有交叉验证。** 三篇都是我一个人的判断。我在自己做评估工具时坚持的「同一输入跑多次看方差」（见 [llm-output-eval](https://github.com/AndyZhang666666/llm-output-eval)），在这个仓库里没有条件做。
- **框架偏向生成类产品。** 六个维度是为 AI 生成类产品定的，拆工具型或平台型产品会不够贴合。

下一步想做的：加一篇工具型产品的拆解（比如一个 AI 编程助手），验证框架在生成类之外是否还成立。如果不成立，比三篇成立的拆解更有价值——说明框架有边界。

## 关于视角

作者曾在百度实习。文库那篇**完全基于公开信息和普通用户使用体验**，不包含也不暗示任何内部数据、文档或口径。文内有声明，这里再说一次。三篇同样适用。
